# Contributing

Bug reports, fixtures and patches are welcome. The most useful single thing
you can send is a **file xenolith gets wrong**: a host it flags that is fine,
an embed it misses, an extraction that changes behaviour. A minimal
reproducing file is worth more than a description of one, and it becomes a
fixture once the fix lands.

Before a larger change, open an issue first: the spec decides what the tool
does, and a patch against a rule the spec does not hold yet starts with a
spec change.

## Getting a working tree

Everything — the Rust toolchain, the linters, the gate runner and the spec
tools — comes from the flake. Nothing is assumed installed.

```sh
nix develop        # or: direnv allow  (the .envrc is `use flake`)
```

Entering the shell runs [`scripts/dev/shell-hook.sh`](../scripts/dev/shell-hook.sh),
which installs the git hooks with `hk install`. It refuses loudly rather than
skipping when `hk` is missing, because an ungated tree that looks gated is
worse than one that says so.

## The gate

There is one definition of the gate: [`hk.pkl`](../hk.pkl). The git hooks run
it, and CI ([`ci.yml`](../.github/workflows/ci.yml)) calls the same `hk` rather
than restating the steps, so a laptop and a runner cannot disagree.

| When | What runs |
| ---- | --------- |
| `pre-commit` | the fast set, scoped to the files you changed: `cargo fmt`, clippy with `-D warnings`, `cargo test`, shellcheck, shfmt, bats, nixfmt, statix, deadnix, actionlint, zizmor, taplo, typos, editorconfig, the spec tools (`mth`, `itok`, `sherd`) and byte-level hygiene |
| `commit-msg` | [`scripts/guard/commit-msg.sh`](../scripts/guard/commit-msg.sh) |
| `pre-push`, `hk check --all` | everything above plus `cargo deny`, `cargo hack --each-feature`, the mirror guards, node configs, `xnl check` on this repo, the private-name guard, TDD order and `lychee --offline` |

Run the whole thing yourself with:

```sh
hk check --all
```

Never bypass it with `git commit --no-verify` or `git push --no-verify`. If a
step is wrong, the fix is a change to the step, argued in its own commit —
not a commit that skipped it.

## Spec first

[`SPEC.md`](../SPEC.md) is the law, not a description written afterwards. It
is a federation: the root holds the goal and the node list, and every
directory that owns something has its own `SPEC.md` with its constraints
(`§C`), interfaces (`§I`), invariants (`§V`), tasks (`§T`) and bugs (`§B`).

- A behaviour change starts as a spec change: a new or amended row, cited by
  id (`src/cli:V24`, `languages/ci/just:V180`).
- A bug found gets a `§B` row stating its cause and the rule that now catches
  it.
- Tasks are flipped from `.` to `x` in the commit that finishes them.
- `§N` navigation is generated by `sherd sync`; do not edit it by hand.

## Test first

Every change to behaviour is two commits, in this order
([`scripts/guard/tdd-order.sh`](../scripts/guard/tdd-order.sh) checks it):

1. **RED** — a `test:` commit adding the failing test, fixture or bats file.
2. **GREEN** — a `feat:` or `fix:` commit making it pass.
3. **REFACTOR** — optional, `refactor:`, behaviour unchanged.

Two mirror rules keep tests next to what they cover:

- every Rust file with logic has a sibling `tests.rs` wired with
  `#[cfg(test)] mod tests;`
  ([`scripts/guard/rust-mirror.sh`](../scripts/guard/rust-mirror.sh));
- every shell script under `scripts/` has a bats file at the mirrored path
  under `tests/unit/`
  ([`scripts/guard/bats-mirror.sh`](../scripts/guard/bats-mirror.sh)).

Fixtures are synthetic or anonymised. Never paste a file from a private
repository, and never name one — in code, fixtures, docs or commit messages.

## Commits

One logical change per commit, in
[Conventional Commits](https://www.conventionalcommits.org/) form, with a body
that says **why**:

```text
fix(migrate): check every directory on a listed path

`migrate` screened a listed path by its last component only, so a path
through a symlinked directory reached the engine and aborted the whole
migration. Each directory is checked now, and the entry is reported as
`legacy-missing` instead.

Why: src/cli:B1 -- one bad entry must not abort the migration.
```

The subject type is one of `feat`, `fix`, `docs`, `test`, `refactor`, `perf`,
`build`, `ci`, `chore`, `style` or `revert`. The body must contain a line
starting `Why:`, citing the spec id the change serves. The diff already says
what changed; `Why:` is the only part of the record that cannot be
reconstructed from the tree.

## Pull requests

One change per pull request, small enough to review in one sitting. CI must
be green. Say in the description which spec rows it serves and what you ran.
