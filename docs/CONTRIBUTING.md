# Contributing to xenolith

`xenolith` is built **spec-first**, and federated: the design and the build
queue live in `SPEC.md` files, one per directory that owns something, with a
`§F` table naming the children. A human or an agent drives the loop the same
way. [`AGENTS.md`](../AGENTS.md) is the same loop as a short checklist.

The most useful single thing you can send is a **file xenolith gets wrong**:
a host it flags that is fine, an embed it misses, an extraction that changes
behaviour. A minimal reproducing file is worth more than a description of
one, and it becomes a fixture once the fix lands.

## Get set up

Everything — the Rust toolchain, the linters, the gate runner and the spec
tools — comes from the flake. Nothing is assumed installed.

```sh
nix develop        # or: direnv allow  (the .envrc is `use flake`)
```

Entering the shell runs [`scripts/dev/shell-hook.sh`](../scripts/dev/shell-hook.sh),
which installs the git hooks with `hk install`. It refuses loudly rather than
skipping when `hk` is missing, because an ungated tree that looks gated is
worse than one that says so.

`flake.nix` declares a substituter for the prebuilt `hk`. Nix only honours it
for users in `trusted-users`; everyone else gets a source build, which works
but is slow the first time.

To run the whole gate by hand, or the fixable half:

```sh
hk check --all     # every step, as CI runs it
hk fix             # formatters, and the generated README blocks and notices
```

## The loop

- **The `SPEC.md` files are the queue.** `§T` rows are the work that
  remains: `.` not started, `~` in progress, `x` done and archived. A
  behaviour change starts as a
  new or amended row, cited by id (`src/cli:V24`, `languages/ci/just:V180`).
- **`§V` is the law.** A task cites the invariants it must respect. Read the
  chain — the root `SPEC.md`, then every `SPEC.md` between it and the
  directory you are changing — before starting.
- **Test first.** Every change to behaviour is a RED `test:` commit adding
  the failing test, fixture or bats file, then a GREEN `feat:` or `fix:`
  commit making it pass
  ([`scripts/guard/tdd-order.sh`](../scripts/guard/tdd-order.sh) checks the
  order). Every Rust file with logic has a sibling `tests.rs` wired with
  `#[cfg(test)] mod tests;`, and every shell script under `scripts/` has a
  bats file at the mirrored path under `tests/unit/`.
- **A bug found gets a `§B` row** stating its cause and the rule that now
  catches it. A finished task flips to `x` and is archived in the commit
  that finishes it: `mth archive <node>/SPEC.md` moves its text to
  `SPEC-ARCHIVE.md` and leaves a stub row carrying its id, status and
  citations. Rows are never deleted, so milestones and citations still
  resolve.
- **Ids are monotonic and never reused.** `§N` navigation is generated by
  `sherd sync`; do not edit it by hand.

## The gate

There is one definition of the gate: [`hk.pkl`](../hk.pkl). The git hooks run
it, and CI ([`ci.yml`](../.github/workflows/ci.yml)) calls the same `hk`
rather than restating the steps, so a laptop and a runner cannot disagree.

| when | what runs |
|---|---|
| `pre-commit` | the fast set, scoped to the files you changed: `cargo fmt`, clippy with `-D warnings`, `cargo test`, shellcheck, shfmt, bats, nixfmt, statix, deadnix, actionlint, zizmor, taplo, typos, editorconfig, the spec tools (`mth`, `itok`, `sherd`), the generated README blocks and notices, and byte-level hygiene |
| `commit-msg` | [`scripts/guard/commit-msg.sh`](../scripts/guard/commit-msg.sh) |
| `pre-push`, `hk check --all` | everything above plus `cargo deny`, `cargo hack --each-feature`, the coverage floor and lint-debt ratchets, the mirror guards, node configs, crate dependency shape, `xnl check` on this repo, the private-name guard, TDD order, every generated output compared unscoped, and `lychee --offline` |

[`INTEGRATION.md`](INTEGRATION.md) has the full picture: which files each
stage sees, why the cargo steps are chained, and how to reproduce any verdict
without hk.

## The one hard rule

**Never `--no-verify`**, on commit or on push. A gate that can be stepped
around is not a gate.

The same applies to the subtler versions — weakening a test, raising a token
ceiling in `.context-limits`, lowering the floor in `.coverage`, or silencing
a lint to get past it. If a rule is wrong, that is a real and welcome
finding: change the rule deliberately, in its own commit, with the reason
recorded. The objection is to routing around a verdict, not to disagreeing
with one.

## Never hand-edit a generated block

The README's badge block and Languages table, and all of
[`THIRD-PARTY-NOTICES.md`](THIRD-PARTY-NOTICES.md), are rendered by
`xenolith-dev` (the unpublished workspace member in [`dev/`](../dev/SPEC.md))
from the files that own each fact. Editing the output *is* the drift the gate
reports. Change the owner — `Cargo.toml`, `hk.pkl`, `.coverage`, a spec — and
regenerate:

```sh
cargo run -q -p xenolith-dev -- --fix      # or: hk fix
cargo run -q -p xenolith-dev -- --check    # what the gate runs
```

## Things that will get a patch turned down

- **A bypassed or weakened gate.** See above.
- **A claim with no evidence.** "This is faster" invites a measurement; "this
  rule is wrong" invites the file that shows it.
- **A fix aimed at the symptom.** If a check fires, the question is what it
  found, not how to stop it firing.
- **A rule with no runner.** An invariant that no test, guard or gate step
  executes is a comment with a number on it.
- **A private repository named, or a private file pasted.** Fixtures are
  synthetic or anonymised — in code, fixtures, docs and commit messages.

## Reporting a bug

Open an issue with what you ran, what you expected, and what happened, and
attach the smallest file that shows it. Before a larger change, open an issue
first: the spec decides what the tool does, and a patch against a rule the
spec does not hold yet starts with a spec change.

Security issues go privately instead — see [SECURITY.md](SECURITY.md).

## Commits

One logical change per commit, in
[Conventional Commits](https://www.conventionalcommits.org/) form, with a body
that says **why**:

```text
fix(migrate): check every directory on a listed path

`migrate` screened a listed path by its last component only, so a path
through a symlinked directory reached the engine and aborted the whole
migration. Each directory is checked now, and the entry is reported as
`legacy-missing` instead.

Why: src/cli:B1 -- one bad entry must not abort the migration.
```

The subject type is one of `feat`, `fix`, `docs`, `test`, `refactor`, `perf`,
`build`, `ci`, `chore`, `style` or `revert`. The body must contain a line
starting `Why:`, citing the spec id the change serves; the commit-msg hook
refuses one without it. The diff already says what changed; `Why:` is the
only part of the record that cannot be reconstructed from the tree.

One change per pull request, small enough to review in one sitting. CI must
be green. Say in the description which spec rows it serves and what you ran.
